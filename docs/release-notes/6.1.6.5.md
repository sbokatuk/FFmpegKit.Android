## What's changed

FFmpeg stays on `n6.1.6`, now from FFmpegKit release [`6.0.4`](https://github.com/ffmpegkit-maintained/ffmpeg/releases/tag/v6.0.4-lts-android) (previously `6.0.3`). The FFmpeg version hasn't moved, so this is the next binding revision, `6.1.6.5`. If you use the `6.*` range, your next restore moves you onto it.

Update if you use `6.1.6.4`: it has two bugs that can stop FFmpeg working in your app.

### Fixed: FFmpeg fails to load on some Android versions

On an arm64 Android 12 (API 31) emulator, `Min`, `MinGpl`, `Https`, `HttpsGpl` and `Video` from `6.1.6.4` could not run any FFmpeg command. The first one threw:

```
java.lang.UnsatisfiedLinkError: dlopen failed: can't enable GNU RELRO protection for ".../libswresample.so": Out of memory
```

This has nothing to do with available memory. In those builds the library's RELRO segment ends past its last loaded segment, so Android's linker tries to protect memory that isn't mapped. Upstream traces this to NDK r26c and now builds with r27c.

All five variants now pass every device check on that emulator. `Video` from `6.1.6.4` did load on an API 35 emulator and on a Pixel 10 with Android 17, so whether you hit this depends on the Android version. Other versions were not tried. Nor was `x86_64`, where `Audio` carries the same defect as these five.

### Fixed: the app freezes after an FFmpeg command

An app on the default Mono runtime could freeze for good at the first garbage collection after it ran an FFmpeg command, usually ending in Android's "isn't responding" dialog. How soon that happened depended on how much the app allocated, so a small test app could run for a long time without showing it. A device check that forces collections after FFmpeg has run never finishes on `6.1.6.4`, and passes on this release.

Mono on Android restarts the threads it stopped for a collection with `SIGXCPU`. FFmpeg installs its own `SIGXCPU` handler when a command runs, so the restart never reached Mono and those threads stayed suspended. FFmpeg also treats that signal as a request to stop.

The packages now call `FFmpegKitConfig.IgnoreSignal(Signal.Sigxcpu)` the first time you use `FFmpegKit`, `FFmpegKitConfig` or `AsyncFFmpegExecuteTask`, so you don't need to change any code. If you already make that call yourself, it is harmless and you can remove it. Your own Java code still has to make the call if it starts FFmpeg without going through those types.

### Security

Upstream reports that FFmpegKit `6.0.4` backports fixes for two issues onto `n6.1.6`:

- **CVE-2026-64830**: VobSub demuxer, unbounded writes past `vobsub->q[]`.
- **CVE-2026-64835**: ADX decoder, channel state desync.

`FFmpegKitConfig.FFmpegVersion` reports `n6.1.6` with or without them, so check the package version instead.

### Native changes

- **`drawtext` is now in `Full`, `FullGpl` and `Video`.** FFmpegKit built HarfBuzz but never enabled it, so FFmpeg silently left the filter out. A command using `drawtext` failed on `6.1.6.4` with `No such filter: 'drawtext'`, and now renders text.
- **A `-filter_complex` parse error no longer kills the process**, according to upstream. This could not be confirmed here: a graph naming an unknown filter returned an error on both `6.1.6.4` and this release.
- **`Min` and `Https` now carry `libc++_shared.so`**, as the other variants already did. That adds about 1.7 MB on `arm64-v8a` and 1.5 MB on `x86_64` before compression.
- **`libc++_shared.so` is now 16 KB-aligned**, like every other library in the packages. Upstream notes that Google Play stops accepting updates without 16 KB support on 1 February 2027.

### .NET API

The FFmpegKit update changes nothing here: `classes.jar` is byte-identical between FFmpegKit `6.0.3` and `6.0.4` in all eight variants.

`6.1.6.4` came out before `8.1.2.5`, so this release also picks up that release's binding changes:

- **`FFmpegKitConfig.DisableLogCallback()`** and **`DisableStatisticsCallback()`** clear the global callbacks.
- The hand-written additions now have **nullable reference annotations**, which can produce new compiler warnings in projects with nullable checks on.
- Every package now warns at build time: **`FFMPEGKIT001`** when `SupportedOSPlatformVersion` is below 24, and **`FFMPEGKIT002`** when a build includes 32-bit runtime identifiers. You can suppress either with `NoWarn`.

Target frameworks, `arm64-v8a` and `x86_64`, `minSdkVersion` 24 and licensing are unchanged.

### FFmpegKit `6.0.3` can no longer be built from `main`

FFmpegKit `6.0.4` packages the same FFmpeg, and [`build/native-versions.tsv`](https://github.com/sbokatuk/FFmpegKit.Android/blob/main/build/native-versions.tsv) has one row per FFmpeg version, so it replaces `6.0.3` there. `6.1.6.4` stays on nuget.org, but it has none of the fixes above.

### What was tested

Against the packed packages:

- An arm64 API 35 emulator and a Pixel 10 with Android 17: all eight variants on `net10.0-android36.0`, plus `Full` and `Video` on `net8.0-android34.0`. Every device check passes, including the garbage collection check, and `FFmpegKitConfig.FFmpegVersion` reports `n6.1.6`.
- An arm64 API 31 emulator: `Min`, `MinGpl`, `Https`, `HttpsGpl` and `Video` on `net10.0-android36.0`.
- The example app on both of the first two devices, on `net10.0-android36.0`, `net9.0-android35.0` and `net8.0-android34.0`: media probe, resize, grayscale and audio extraction, then playback of the result.
- `drawtext` in `Video`, `Full` and `FullGpl`.
- All 190 package tests.

`x86_64` was not run on a device.
