## What's changed

FFmpeg moves from `n8.1.2` to **`n8.1.3`**, from FFmpegKit release [`8.1.9`](https://github.com/ffmpegkit-maintained/ffmpeg/releases/tag/v8.1.9-lts-android) (previously `8.1.7`). Package versions follow FFmpeg, so this is `8.1.3.1`, the first binding revision of the new FFmpeg. If you use the `8.*` range, your next restore moves you onto it.

This release also fixes a freeze that affects `8.1.2.5`, so update if your app runs FFmpeg commands.

### Fixed: the app freezes after an FFmpeg command

An app on the default Mono runtime could freeze for good at the first garbage collection after it ran an FFmpeg command, usually ending in Android's "isn't responding" dialog. How soon that happened depended on how much the app allocated, so a small test app could run for a long time without showing it.

Mono on Android restarts the threads it stopped for a collection with `SIGXCPU`. FFmpeg installs its own `SIGXCPU` handler when a command runs, so the restart never reached Mono and those threads stayed suspended. FFmpeg also treats that signal as a request to stop.

The packages now call `FFmpegKitConfig.IgnoreSignal(Signal.Sigxcpu)` the first time you use `FFmpegKit`, `FFmpegKitConfig` or `AsyncFFmpegExecuteTask`, so you don't need to change any code. If you already make that call yourself, it is harmless and you can remove it. Your own Java code still has to make the call if it starts FFmpeg without going through those types.

### Security

Upstream reports that FFmpeg `n8.1.3` closes two issues reachable in this build:

- **CVE-2026-64830**: VobSub demuxer, unbounded writes past `vobsub->q[]`.
- **CVE-2026-64835**: ADX decoder, channel state desync.

It lists two others from the same batch, CVE-2026-64831 (Vulkan HEVC) and CVE-2026-64832 (NVDEC), as not reachable, because neither path is compiled for Android. The matching VobSub and ADX fixes are in [FFmpeg's `n8.1.3` changes](https://github.com/FFmpeg/FFmpeg/compare/n8.1.2...n8.1.3).

### Native changes

- **`drawtext` is back in `Full`, `FullGpl` and `Video`.** FFmpegKit built HarfBuzz but never enabled it, so FFmpeg silently left the filter out. Both `--enable-libharfbuzz` and the filter are in the shipped libraries now.
- **A `-filter_complex` parse error no longer kills the process**, according to upstream. It traced this to the failure path freeing an uninitialised pointer, which any unknown filter name could reach.
- **`Min` and `Https` now carry `libc++_shared.so`**, as the other variants already did. That adds about 1.8 MB per ABI before compression.

### .NET API

No changes. `classes.jar` is byte-identical between FFmpegKit `8.1.7` and `8.1.9` in all eight variants, and the generated API matches.

Target frameworks, `arm64-v8a` and `x86_64`, `minSdkVersion` 24 and licensing are also unchanged.

### Staying on FFmpeg 8.1.2

`8.1.2.5` stays on nuget.org, and [`build/native-versions.tsv`](https://github.com/sbokatuk/FFmpegKit.Android/blob/main/build/native-versions.tsv) keeps its `8.1.2` row, so FFmpegKit `8.1.7` can still be rebuilt. It has neither the security fixes nor the freeze fix.

### What was tested

Against the packed packages, on an arm64 API 35 emulator:

- All eight variants on `net10.0-android36.0`, plus `Full` and `Video` on `net8.0-android34.0`: every device check passes, including a new one that forces garbage collections after FFmpeg has run, and `FFmpegKitConfig.FFmpegVersion` reports `n8.1.3`.
- The example app on `net10.0-android36.0` and `net9.0-android35.0`: media probe, resize, grayscale and audio extraction, then playback of the result.
- All 190 package tests.
